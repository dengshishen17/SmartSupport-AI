## 一、检索评测（RAG）

### 1.1 四种召回策略横向对比

同一份 75 条标注用例，四种召回策略在完全相同的条件下跑出来的结果：

| 策略 | Hit@1 | Hit@3 | Hit@5 | MRR | NDCG@5 | MAP | 平均延迟 | 越界最高分 |
|---|---|---|---|---|---|---|---|---|
| Dense | 81.3% | 97.3% | 98.7% | 0.8878 | 0.8871 | 0.9092 | 285.5 ms | 0.4891 |
| BM25 | 76.0% | 92.0% | 93.3% | 0.8338 | 0.8919 | 0.8864 | **29.9 ms** | **3.8358** |
| Hybrid | 81.3% | 94.7% | 100% | 0.8847 | 0.9002 | **0.9384** | 304.8 ms | 0.0164 |
| **Rerank（最终选用）** | **89.3%** | **97.3%** | **100%** | **0.9400** | **0.9048** | 0.8970 | 268.9 ms | 0.6785 |

**结论**：Rerank 在 Hit@1 上比次优策略（81.3%）高 **8 个百分点**，MRR 高 0.055，最终选用 Rerank 作为默认策略。

**这张表里有两个值得说的点**：

1. **BM25 越界最高分 3.8358 vs Hybrid 0.0164** —— 纯关键词检索在「退货/换货」「保修/价保」这类近义词上会命中错误章节，且分数虚高。混合检索通过向量语义压制了这一问题。
2. **Rerank 的 MAP（0.8970）反而低于 Hybrid（0.9384）** —— MAP 衡量的是所有相关文档的平均精度位置，而本评测集对**近义干扰章节做了分级惩罚**，Hybrid 把干扰项排得更靠后，MAP 反而占优。这说明单一指标会失真，必须多指标交叉看。

### 1.2 分级相关性与干扰项设计

评测集的 `ground truth` **不标注 chunk id**，只标注**期望章节标题**。

原因：向量库主键是随机生成的 UUID，跨次导入不稳定，用 chunk id 标注会导致评测集无法复用。改用章节标题后，评测集可以长期保持有效。

相关性分级：

| 等级 | 含义 |
|---|---|
| Primary（3） | 期望章节本体 |
| Secondary（2） | 同章节内相关条款 |
| Tertiary（1） | 相关但非核心条款 |
| Distractor（-1） | 近义干扰章节（如「退货」之于「换货」） |

**干扰项是刻意设计的**：如果评测集全是容易的问题，Hit@1 必然接近 100%，那样的数字没有意义。加入干扰项后，89.3% 才是一个真实的、反映检索鲁棒性的指标。

## 二、Agent 轨迹评测（ReAct）

### 2.1 为什么要做轨迹级评测

只评最终回答（结果正确）无法区分两种情况：

- Agent 检索为空，凭模型自身知识答对了 → **结果对，过程错**
- Agent 调了 5 次无关工具才凑出答案 → **结果对，过程低效**
- Agent 对越界问题调用了业务数据工具 → **结果可能对，但存在数据安全风险**

60% 以上的 AI 岗位 JD 明确要求评测能力。**能做到过程级诊断，是「会调 API」和「会做 Agent 工程」的分水岭。**

### 2.2 实测结果（114 条用例，React 链路）

| 指标 | 值 |
|---|---|
| 用例总数 / 执行成功 / 成功 | 114 / 114 / **114** |
| **pass@1**（工具调用步数 ≤1 且回答忠实） | **89.5%** |
| **pass@3**（工具调用步数 ≤3 且回答忠实） | **96.5%** |
| **引用忠实度** | **96.5%** |
| 平均工具调用步数 | 0.87 |
| **无效调用率** | **0.0%**（0 / 99） |
| **浪费调用率** | **0.0%**（0 / 99） |
| 降级工具调用 | 0 |
| 工具调用总数 | 99 |
| 平均总延迟 | 2040.5 ms |
| 平均 Token 消耗 | 2239.6（prompt 2096.1 / completion 143.5） |
| 平均 LLM 轮次 | 1.8 |

步数分布：`0 步 23 条` / `1 步 83 条` / `2 步 8 条` —— **绝大多数问题一次工具调用即收敛**。

### 2.3 分类别表现

| 类别 | 用例数 | pass@1 | pass@3 | 忠实度 |
|---|---|---|---|---|
| 越界问题（应拒答） | 19 | **100%** | **100%** | **100%** |
| 口语化提问 | 8 | **100%** | **100%** | **100%** |
| 政策问答 | 63 | 90.5% | 93.7% | 93.7% |
| 工具调用类 | 24 | 75.0% | **100%** | **100%** |

**越界问题 100% 通过** —— 这是安全底线，19 条全部正确拒答，没有一条把真实订单数据喂给越界提问。

**工具类 pass@1 75% 但 pass@3 100%** —— 说明工具选型本身正确（忠实度 100%），只是部分复合问题需要两次调用才能收敛，不是选错工具。

### 2.4 失败归因

| 分类 | 数量 | 说明 |
|---|---|---|
| `RETRIEVAL_EMPTY` | 6 | 检索未命中条款 |
| `HALLUCINATION` | 4 | 回答出现参考要点之外的政策条款或业务数据 |

114 条里只剩 10 条失败，且失败原因全部归类清晰 —— 这正是轨迹级评测的价值：**能定位到具体失败类型，而不是只看到一个平均分。**

### 2.5 一个真实的踩坑与修复

> **初版参考答案只写了 1 句摘要**，模型引用完整条款反被判 HALLUCINATION，pass@1 一度只有 **64.9%**，幻觉判定 35 条。
>
> **根因不在模型，在评测集本身** —— 参考答案不完整，裁判模型无法判断模型引用的是「正确但更详细」还是「编造」。
>
> **修复**：重写参考答案使其覆盖完整条款要点 + 修正裁判 Prompt 中的忠实度判定标准。修复后 **pass@1 → 89.5%，幻觉 35 条 → 4 条**。
>
> 这条经验写在这里是因为它比数字本身更重要：**评测集的参考答案质量，直接决定了评测结论的可信度**。参考答案写得不严谨，评测就会变成自欺欺人。

## 三、Prompt 版本化回归

### 3.1 机制

Prompt 按 `name + version` 注册（`app/prompts.py`），带内容 hash，可随时对比两版差异。改动不会直接上线，而是先跑回归。

### 3.2 回归设计

- **样本**：84 条用例
- **轮次**：2 轮（同一批样本跑两遍，取中位数）
- **交错执行**：基线版与候选版**交替跑**，避免把「模型服务的时间段波动」误判成「Prompt 的效果」
- **噪声带**：同一版本自身两轮之间的差异作为噪声带，指标变化超出噪声带才判定为显著变化

### 3.3 实测结果

| 指标 | 基线 v1 | 候选 v2 | Delta | 噪声带 | 判定 |
|---|---|---|---|---|---|
| **拒答率** | 96.43% | **98.21%** | **+1.78pt** | 0.84pt | **IMPROVED** ✅ |
| 引用忠实度 | 97.03% | 97.62% | +0.59pt | 0.84pt | 无显著变化 |
| 工具规则遵守率 | 100% | 100% | 0 | 0 | 无显著变化 |
| 成功率 | 100% | 100% | 0 | 0 | 无显著变化 |
| 平均延迟 | 1602.7 ms | 1608.3 ms | +5.6 ms | 198.5 ms | 无显著变化 |

**v1**：抽取「9 条处理要点」+ 250 字上限（改造前线上版本）
**v2**：强制先查再答、显式禁止编造条款、口语化提问不算越界、去掉末尾转人工兜底话术

**决策**：v2 拒答率提升 1.78pt 超出噪声带，其余指标无退化 → **升级为默认版本**。

### 3.4 为什么用「中位数 + 噪声带」而不是直接比平均值

LLM 评测天然有随机性。同样 84 条跑两遍，某版忠实度可能波动 ±1pt。如果直接比两版平均值，**小幅波动会被误判成「改进」或「退化」**，然后基于错误结论改 Prompt，越改越偏。

用同一版本自身两轮的波动范围作为噪声带，**只有超过噪声带的差异才算数** —— 这是把 Prompt 当代码资产管理的关键前提。

## 四、可观测性（Trace）

| 指标 | 值 |
|---|---|
| Trace 结构 | 根 span（`rag_chat` / `react_chat`）→ 阶段 span（`retrieval` / `context` / `agent` / `tool` / `llm`） |
| 存储 | SQLite（`python-service/ops.db`） |
| 前端视图 | span 树可视化 + 慢 span 排行（`frontend/src/views/TraceView.vue`） |
| 隔离 | 单测通过 `SMART_OPS_DB` 环境变量写入临时库，不污染生产观测数据 |

**一次真实请求的 span 树实测**（`eval-final-metrics.json` 的 `trace` 段）：

| span 类型 | 数量 | 平均耗时 | 最大耗时 | 错误数 |
|---|---|---|---|---|
| `retrieval` | 6 | 8.38 ms | 50.25 ms | 0 |
| `step`（Agent 步） | 11 | 1.24 ms | 10.32 ms | 4 |
| `llm` | 2 | 0 ms | 0 ms | 0 |
| `context` | 1 | 0 ms | 0 ms | 0 |

**与普通日志的区别**：普通日志是「每次请求一行」，只能回答「这次慢了」；span 树能回答「**到底是检索慢、上下文组装慢、工具慢还是模型生成慢**」。慢 span 排行直接给出瓶颈定位。

> `llm` 与 `context` 的耗时为 0，是因为这条 trace 记录来自一次 **RAG 直答链路**（`app/agent.py`）：该路径下 `llm` span 用 `tr.record()` 记录 —— 这是 `trace.py` 里专门为「统计类信息」提供的零耗时 span（见 `trace.py` 的 `record()` 方法注释：「记录一个已完成、零耗时的 span」）。真实耗时记在根 span 的 `total` 上。
>
> 而 ReAct 链路（`app/workflow.py`）用的是 `tr.span(...)` 上下文管理器，会正常记录耗时。两种写法的区别是：**流式生成不适合计入单 span 耗时**（分片到达会导致统计失真），所以统一记在请求级 total 上。
>
> `step` 类型的 4 个错误对应第二节里 `TOOL_ERROR` 分类的记录 —— 注意它与 `RETRIEVAL_EMPTY`（检索未命中）是**两个不同的失败分类**（见 `eval_agent.py` 的 `classify_failure()`）。Trace 里能定位到具体 span，评测报告里能归类到具体 taxonomy，两边可以互相印证。

## 如何复现

```bash
cd python-service

# 1. 离线单元测试（零 API 消耗，154 个）
python -m eval.test_context
python -m eval.test_ndcg
python -m eval.test_trace
python -m eval.test_prompt_version
python -m eval.test_tool_runtime
python -m eval.test_eval_agent
python -m eval.test_rerank_authority

# 2. 检索评测（75 条 + 15 条越界，4 种策略对比）→ eval/eval-retrieval-result.json
#    全程只读向量库，不调 LLM，零 API 消耗，结果确定性可复现
python -m eval.eval_retrieval --modes=dense,bm25,hybrid,rerank --topk=5 --cases=both

# 3. Agent 轨迹评测（114 条）→ eval/eval-agent-result-react.json
python -m eval.eval_agent --mode=react --cases=both

# 4. Prompt 回归（84 条 × 2 轮 × 2 版本）→ eval/eval-prompt-regression-result.json
python -m eval.eval_prompt_regression --baseline=rag_system:v1 --candidate=rag_system:v2 --rounds=2 --cases=both

# 5. 汇总所有指标 → eval/eval-final-metrics.json
python -m eval.collect_final_metrics
```

> **参数格式说明**：这三个脚本手动解析 `sys.argv`，统一用 `--flag=value` 形式（**等号连接，不空格**）。`--cases=both` 表示「基础集 + 扩展集」合并，也就是简历里那些数字对应的完整评测集。

**成本说明**：步骤 1、2 零 API 消耗；步骤 3、4 需要真实调用 DeepSeek（114 条 × 1.8 轮 + 84 条 × 2 轮 × 2 版本），单次全量约 0.5 元。

**原始结果文件**（全部在 `python-service/eval/`）：

| 文件 | 内容 |
|---|---|
| `eval-final-metrics.json` | 本报告所有数字的机器可读来源 |
| `eval-retrieval-result.json` | 四种召回策略逐条检索明细 |
| `eval-agent-result-react.json` | 114 条 Agent 逐条轨迹（含工具调用明细） |
| `eval-prompt-regression-result.json` | Prompt 回归逐轮明细 |
| `eval-stability-react.json` | 稳定性评测（同一用例多次运行的一致性） |
| `rerank-weight-tuning.json` | 重排器权重调参过程记录 |

**环境要求**：Python 3.10+、`pgvector`（PostgreSQL 16 + pgvector）、DeepSeek API Key、百炼 API Key。向量库为空时先跑 `python -m app.ingest` 导入知识库语料。
