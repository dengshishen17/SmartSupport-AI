## 一、为什么要扩充语料

上一版评测基于 6 个 chunk / 29 条用例，四个检索策略的指标全部挤在
「Hit@3 = 100%」的天花板上（dense / bm25 / hybrid / rerank 的 Hit@1 差异仅 10pt 以内），
**无法区分策略优劣**，优化工作缺少可度量的目标。

扩充后：
- 知识库：6 chunk → **24 chunk**（原 6 个保持不变 + 新增 18 个扩展章节）
- 评测集：29 条可答 + 4 越界 → **75 条可答 + 15 越界**
- 新增 **8 条「近义干扰」用例**：词面高度相似但语义不同
  （退货 vs 换货、保修 vs 价保、退款 vs 优惠券、物流查询 vs FAQ）

## 二、扩展语料设计

新增文档《售后政策扩展数据.md》，9 个章节：

| 章节 | 章节 | 章节 |
|---|---|---|
| 七、换货政策 | 十一、常见问题 FAQ | 十四、渠道与自营配送政策 |
| 八、开票与发票政策 | 十二、服务等级与响应时效 | 十五、常见误区澄清 |
| 九、优惠券与活动规则 | 十三、客服话术与信息脱敏规范 | |
| 十、价格保护与价保规则 | | |

设计要点：**刻意制造近义干扰**。

| 干扰对 | 表面相似点 | 语义差异 |
|---|---|---|
| 退货(二) vs 换货(七) | 都是「签收后 7 天 / 15 天」，时限完全一致 | 运费责任规则相反；换货完成后不自动创建退款记录 |
| 退款(一) vs 优惠券(九) | 都涉及金额计算 | 退款按实付退回，优惠券不返还 |
| 保修(四) vs 价保(十) | 都是「签收后 N 天内」 | 保修是修，价保是退差价；价保仅限自营常规商品 |
| 物流查询(三) vs FAQ(十一) | 都覆盖「快递没到」 | FAQ 是复述，政策是规则定义 |
| 开票(八) vs 优惠券(九) | 都涉及金额差异 | 发票金额差异源于优惠券/运费补贴 |

## 三、实测结果（75 条可答用例，topK=5）

| 策略 | Hit@1 | Hit@3 | Hit@5 | MRR | 平均延迟 | 越界 top 分 |
|---|---|---|---|---|---|---|
| dense | 81.3% | 97.3% | 98.7% | 0.8878 | 264ms | 0.489 |
| bm25 | 76.0% | 92.0% | 93.3% | 0.8338 | **26ms** | 3.836 |
| hybrid | 81.3% | 94.7% | 100% | 0.8847 | 310ms | 0.016 |
| **rerank** | **89.3%** | 97.3% | **100%** | **0.9400** | 263ms | 0.679 |

### 与扩充前的对比

| 策略 | 扩充前 Hit@1 | 扩充后 Hit@1 | 扩充前 MRR | 扩充后 MRR |
|---|---|---|---|---|
| dense | 89.7% | 81.3% | 0.9483 | 0.8878 |
| bm25 | 75.9% | 76.0% | 0.8161 | 0.8338 |
| hybrid | 89.7% | 81.3% | 0.9483 | 0.8847 |
| **rerank** | 79.3% | **89.3%** | 0.8966 | **0.9400** |

**关键结论**：

1. **dense 的「89.7%」是语料太小的假象**。扩充后 dense 掉到 81.3% —— 原来的高分
   只是因为 6 个 chunk 少、干扰少，没有区分度。
2. **rerank 从负收益变成正收益**。扩充前 Hit@1 79.3%（比 dense 低 10.4pt），
   扩充后 89.3%（比 dense 高 8.0pt）。**没有足够的干扰语料，就无法证明优化有效。**
3. **bm25 延迟是 dense 的 1/10**（26ms vs 264ms），但 Hit@1 低 13.3pt。
   中文场景下纯关键词召回对「换货」这类政策术语的覆盖有限。
4. **hybrid（RRF）没有优于 dense**。RRF 按排名倒数融合，
   当 dense 已达 Hit@5=100% 时，BM25 引入的噪声抵消了它带来的补充。

## 四、重排器的两个关键改进

### 4.1 来源权威度信号（新增第四个信号）

扩充语料后暴露一个系统性问题：**口语化查询被 FAQ 章节「截胡」**。

「钱什么时候能退到我卡上」「快递怎么还没到」「东西坏了找谁修」——
这些问法在《常见问题 FAQ》里被原样复述，语义检索必然把 FAQ 排在政策原文前面。
从检索角度 FAQ 是对的，从产品角度应当优先返回政策原文（更权威、可追溯）。

因此新增「来源权威度」这一显式信号：

| 章节类型 | 权重 | 理由 |
|---|---|---|
| 政策正文（§1~§5、§7~§10、§12、§14） | 1.00 | 规则定义本身 |
| 快速参考表 / 常见误区澄清 | 0.70 | 对政策的归纳，不新增规则 |
| 常见问题 FAQ | 0.35 | 政策改写成口语问法后的复述 |

这是可解释的领域先验，不是针对评测集的过拟合 —— 每一条都能讲清楚为什么。

### 4.2 向量分量改用绝对刻度（修复一个隐性 bug）

原实现对四个分量统一做 min-max 归一化。但向量相似度本身是有意义的绝对值
（0.70 vs 0.66 只差 4pt），min-max 会把它拉伸成「1.0 vs 0.0」，
**等于把噪声放大成信号**。

实测验证：查询「钱什么时候能退到我卡上」时
```
query tokens: ['钱什','什么','么时','时候','候能','能退','退到','到我','我卡','卡上']
FAQ    kw=1.000  auth=0.35     ← 字面完全匹配
POLICY kw=0.000  auth=1.00     ← 章节名不含这些词
```
min-max 把向量分 0.70 vs 0.66 拉伸成 1 vs 0，FAQ 稳定压过政策正文。

修正：向量分量用绝对刻度（`_norm_absolute`），关键词/章节分量仍在候选池内做相对归一化。
修正后 rerank Hit@1 从 89.3% → 90.7%。

权威度同时以**乘性折扣**参与排序：
```
final = (0.55·vec + 0.20·kw + 0.15·sec + 0.10·auth) × (0.85 + 0.15·auth)
```
乘性折扣是必要的 —— FAQ 的问法与用户口语几乎逐字相同，
关键词与向量两项都天然偏向 FAQ，只有乘性折扣能保证
FAQ 必须「语义明显更优」才能压过政策正文。

## 五、避免过拟合：dev/test 分割调参

重排器有四个信号权重。在全部 75 条用例上调权重、再在同一份数据上报告指标，
等于把评测集当训练集用。

因此实现 `eval/tune_rerank_weight.py`：
- 按 id 哈希稳定二分（dev 36 条 / test 39 条，每次划分一致）
- 只在 dev 上搜权重网格（37 组，总和为 1）
- 选定后只在 test 上看一次

| 指标 | dev（调参集，36 条） | test（未见集，39 条） |
|---|---|---|
| Hit@1 | 91.7% | **87.2%** |
| Hit@3 | 100% | 94.9% |
| MRR | 0.9583 | 0.9175 |

**对比当前默认权重 (0.55/0.20/0.15/0.10) 在同一 test 集上**：
Hit@1 87.2%（完全相同）、MRR 0.9231（略高于调参选出的 0.9175）。

**结论：在 75 条规模上做权重微调，收益落在噪声范围内，不值得做。**
当前权重本身就是 dev MRR 最高的一组之一，且在 test 上 MRR 最优。
这个结论本身比「我又调出了 0.5% 提升」更有价值 ——
它说明这套评测的样本量已经接近可分辨的临界点，
继续扩语料、扩用例比继续调参更重要。

## 六、评测口径的两处修正

扩充过程中发现两个评测本身的缺陷（不是模型的问题）：

### 6.1 section 解析漏掉了长章节的后续段落

`ingest.split_markdown` 把长章节按 512/50 切成多段，
后续段落的正文里**没有 `## ` 标题**（只有 `### 小节标题` 或直接是正文），
但 `metadata.section` 里有。原实现只从正文解析 `## `，
导致这些 chunk 的 section 恒为 None，**评测无法判断它们是否命中**。

修正：`Document.section` 优先取 `metadata.section`，回退到正文解析；
`to_dict()` 额外带出 `section` 字段。

### 6.2 ground truth 未考虑多合法来源

「钱什么时候能退到我卡上」在《一、退款政策》和《十一、常见问题 FAQ》里
**都是正确来源**。原评测只认政策正文，导致 dense 明明答对了却被判失败。

修正：`expectedSections` 支持多个合法章节，命中任意一个即算命中。
涉及口语化改写（5 条）、常见问题 FAQ（5 条）、快速参考表（2 条）、
误区澄清（4 条）共 16 条用例。

修正后 dense Hit@1 从 68.0% → 81.3% —— **其中 13.3pt 是评测口径修正带来的**，
不是模型能力变化。这说明：如果没有扩充语料，这批缺陷根本不会暴露。

## 七、扩展语料带来的其他工程修复

### 7.1 embed_batch 未分批（真实 bug）

语料从 6 chunk 扩到 18 chunk 时触发：
```
openai.BadRequestError: 400 InternalError.Algo.InvalidParameter:
Value error, batch size is invalid, it should not be larger than 10
```
百炼 `text-embedding-v4` 限制单次 `input` 不超过 10 条，
而 `embeddings.embed_batch` 一次性传入全部文本。
原实现只在 6 chunk 时没暴露 —— **典型的「小数据量掩盖的 bug」**。

修正：按 10 条一批自动分批。

### 7.2 Rerank 默认策略从 dense 改为 rerank

扩充语料后 rerank 全面优于 dense（Hit@1 +8.0pt、Hit@5 +1.3pt、MRR +0.052），
因此把 `RETRIEVAL_MODE` 默认值从 `dense` 改为 `rerank`。
可通过环境变量 `RETRIEVAL_MODE=dense` 回退。

## 八、Agent 端到端验证（30 条用例，扩充语料后）

| 指标 | 扩充前 | 扩充后 |
|---|---|---|
| pass@1 | 86.7% | 83.3% |
| pass@3 | 93.3% | 86.7% |
| 忠实度 | 93.3% | 86.7% |
| 无效调用率 | 0% | 0% |
| 浪费调用率 | 0% | 0% |
| 降级调用数 | 0 | 0 |
| 平均延迟 | 2054ms | 2006ms |
| Token 总量（30 条） | 62226 | **58569（-5.9%）** |
| 平均单请求 Token | 2074 | 1952 |

pass@1 的小幅波动（86.7% → 83.3%）在裁判模型随机波动范围内
（pass@1 依赖 LLM 裁判，同一份用例多次运行有 3~7pt 波动）。
**值得关注的是 Token 总量下降 5.9%** —— 语料扩充后检索能一次命中更准的片段，
模型少读了一些无关内容。

## 九、已知限制与下一步

| 限制 | 说明 |
|---|---|
| **语料仍是合成的** | 扩展文档按真实售后政策结构编写，但非真实企业数据 |
| **未覆盖真实问法分布** | 75 条用例是按章节结构设计的，不是线上真实 query 日志 |
| **裁判模型依赖** | Agent 层 pass@k 有 3~7pt 随机波动，检索层指标是确定性的 |
| **未做 Cross-Encoder 对比** | 规则式重排的效果上限低于 bge-reranker，但引入 torch 不符合轻量部署目标 |
| **权重调参收益不显著** | 见第五节，样本量已接近可分辨临界点 |

### 下一步

| 优先级 | 动作 | 目的 |
|---|---|---|
| 高 | P0-1 上下文预算（`app/context.py`）| 已有 Token 基线（平均 1952/请求），可量化压缩效果 |
| 高 | 扩语料到 50+ chunk + 用例到 150 条 | 让权重调参与策略对比有统计意义 |
| 中 | 引入 Cross-Encoder 重排做 A/B | 量化规则式重排与模型重排的差距，作为技术选型依据 |
| 中 | 多轮会话场景评测 | 验证记忆与上下文累积的退化曲线 |

## 十、可直接引用的结论

> 将 RAG 知识库从 6 个 chunk 扩充到 24 个（新增 9 个章节，含换货/开票/优惠券/价保/
> 服务时效/客服规范等），评测集从 29 条扩充到 75 条（含 8 条近义干扰用例、
> 越界探针扩至 15 条）。
>
> 扩充后暴露出原「Hit@1 89.7%」实为小语料造成的假象，
> 纯向量检索真实 Hit@1 仅 81.3%。为此在重排器中新增「来源权威度」信号
> （政策正文 1.0 / 归纳章节 0.7 / FAQ 复述 0.35），并修正向量分量被 min-max
> 归一化放大噪声的问题（改为绝对刻度）。最终规则式重排 Hit@1 89.3%、MRR 0.9400，
> 相比纯向量召回提升 8.0 个百分点、MRR 提升 0.052。
>
> 通过 dev/test 分割调参验证了收益的可信度：调参集 Hit@1 91.7%，
> 未见集 87.2%，与默认权重持平 —— 说明当前信号权重已接近最优，
> 继续调参收益在噪声范围内，下一步应扩大语料与用例规模。
>
> 过程中修复了 embed_batch 未按百炼 API 10 条上限分批的缺陷，
> 以及评测口径两处问题（长章节后续段落 section 解析失败、
> ground truth 未考虑多合法来源）。
