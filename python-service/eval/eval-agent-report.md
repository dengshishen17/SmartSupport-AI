## 一、为什么需要轨迹级评测

`eval_answer.py` 只评估**结果**（最终回答是否忠实、是否正确拒答、工具选型是否符合预期），
但存在「蒙对」与「走对」混为一谈的问题：

- Agent 第一步检索为空，却凭模型知识答对了 → 结果对、过程错
- Agent 调了 5 次工具才凑出正确回答 → 结果对、过程低效
- Agent 调用了不该调的业务工具（把真实订单数据喂给越界问题）→ 结果可能对，但存在数据安全风险

60% 的国内 AI JD 明确要求评测能力，能做到**过程级诊断**是区分「会调 API」与「会做 Agent 工程」的关键。

## 二、指标定义

### 任务级

| 指标 | 定义 |
|---|---|
| **pass@1** | 工具调用步数 ≤ 1 且 LLM-as-Judge 判定回答忠实 |
| **pass@3** | 工具调用步数 ≤ 3 且判定回答忠实 |
| avgSteps | 平均工具调用步数 |
| stepsDistribution | 步数分布直方图 |

### 调用级

| 指标 | 定义 |
|---|---|
| totalToolCalls | 工具调用总数 |
| invalidCalls | 无效调用数（工具不存在 / 参数非法 / 执行报错） |
| invalidCallRate | 无效调用率 = invalidCalls / totalToolCalls |
| wastedCalls | 浪费调用数（重复调同工具同参数 / 连续同工具形成循环 / 越界问题调用业务数据工具） |
| wastedCallRate | wastedCalls / totalToolCalls |

### 失败归类 taxonomy

| 分类 | 触发条件 |
|---|---|
| `RETRIEVAL_EMPTY` | 检索工具返回「没有检索到相关条文」 |
| `TOOL_ERROR` | 工具返回「库暂时不可用」或抛出异常 |
| `INVALID_ARGS` | 参数缺失/非法，或调用了不存在的工具 |
| `DUPLICATE_CALL` | 同一工具同一参数重复调用 |
| `LOOP` | 连续 3 次调用同一工具 |
| `MAX_STEP` | 超过步数上限（8 步）仍未收敛 |
| `HALLUCINATION` | 裁判判定回答出现参考要点中没有的政策条款或业务数据 |
| `REFUSAL_UNDER` | 越界问题却调用了业务数据工具（订单/退款/工单/保修） |
| `REFUSAL_OVER` | 知识库有答案却整段拒答（实质信息量为零） |

> 指标与加入前的差异来自裁判模型随机波动，两者都在基线区间内）。

### 总体指标

| 指标 | 值 |
|---|---|

| **pass@1** | **86.7%** |
| **pass@3** | **93.3%** |
| 引用忠实度 | 93.3% |
| **平均步数** | **0.9** |
| 最大步数 | 8 |
| 工具调用总数 | 27 |
| **无效调用率** | **0.0%** |
| **浪费调用率** | **0.0%** |
| **降级调用数** | **0** |
| 平均端到端延迟 | 2054ms |

### 步数分布

| 步数 | 用例数 | 占比 | 说明 |
|---|---|---|---|
| 0 步 | 5 | 16.7% | 模型直接作答，未调工具 |
| 1 步 | 23 | 76.7% | 单次工具调用即收敛 |
| 2 步 | 2 | 6.7% | 需要两次调用（如先查订单再查退款） |
| ≥3 步 | 0 | 0% | 无需多轮规划 |

**结论：Agent 收敛性良好。** 83.3% 的用例在 1 步内完成，无重复调用、无循环、无超步数。

### 失败归类分布

| 分类 | 数量 | 占比 | 根因分析 |
|---|---|---|---|
| `HALLUCINATION` | 4 | 13.3% | 回答中出现参考要点未覆盖的条款细节 |
| `RETRIEVAL_EMPTY` | 3 | 10.0% | 订单 99999 / 10007 / 10003 确实无对应记录，**属于正常业务空结果** |
| 其余 7 类 | 0 | 0% | 无工具报错、无参数非法、无重复调用、无循环、无超步数、无过度/不足拒答 |

### 分类维度表现

| 类别 | 条数 | pass@1 | pass@3 | 忠实度 |
|---|---|---|---|---|
| 业务工具（tool） | 12 | 83.3% | **100%** | **100%** |
| 越界拒答（out_of_scope） | 4 | **100%** | 100% | 100% |
| 政策问答（policy） | 10 | 70.0% | 70.0% | 70.0% |
| 口语化（colloquial） | 4 | 75.0% | 75.0% | 75.0% |

**关键观察**：
1. **业务工具类 100% 忠实** —— 工具返回的是真实业务数据，模型直接引用，不存在编造空间。
2. **越界类 100% 通过** —— 且 `REFUSAL_UNDER` 为 0，说明越界问题没有把真实业务数据拉进上下文，
   安全边界有效。
3. **政策类与口语化类是短板**（70% / 75%）。根因是**知识库只有 6 个 chunk**：
   口语化问题（如「东西坏了怎么办」）表述与政策原文措辞差距大，
   检索到的片段覆盖面窄，模型为补全语义而产生了参考要点之外的表述。

## 四、工具可靠性层（当晚补充）
### 保护机制

`app/tool_runtime.py` 的 `ToolExecutor` 为工具执行提供四层保护：

| 保护 | 实现 | 默认参数 |
|---|---|---|
| 超时控制 | `asyncio.wait_for` + 自管 `ThreadPoolExecutor` | 8 秒 |
| 重试 | 指数退避（`backoff * 第几次`）| 2 次，基数 0.3s |
| 熔断降级 | `CircuitBreaker` 状态机 CLOSED→OPEN→HALF_OPEN | 阈值 3 次，冷却 30s |
| 并发限流 | `asyncio.Semaphore` | 8 |

### 接入路径

LangGraph 的 `ToolNode` 直接调用 `tool.invoke()`，**会绕过外部装饰**。
因此可靠性挂在 `ToolNode` 的 `awrap_tool_call` 钩子上，并把 `ToolNode` 实例
直接传给 `create_react_agent`（该函数接受 ToolNode 实例，此时不重建节点）。

```
LangGraph ToolNode → awrap_tool_call → ToolExecutor（超时/重试/熔断/限流）→ 底层工具
```

### 关键实现细节（踩过的坑）

**坑 1：同步阻塞工具必须放线程池**。业务工具是阻塞式 MySQL 查询，直接调用会卡死事件循环，
`asyncio.wait_for` 无法中断它 —— 实测 0.5s 超时实际跑了 3s。

**坑 2：不能用 `asyncio.to_thread`**。它使用 asyncio 默认线程池，事件循环关闭时会等待池内线程结束，
导致「超时后总耗时仍被拖长」（实测 2.3s）。改用自管 `ThreadPoolExecutor` + `loop.run_in_executor`，
超时后立即放弃等待并返回降级话术。

**坑 3：不能先调用再判断是否协程**。`raw = fn(args)` 后再判断会让同步函数被**执行两遍**
（一次在事件循环里，一次在线程池里）。必须用 `iscoroutinefunction` 预先判断。

### 故障注入实测

| 场景 | 观测结果 |
|---|---|
| 正常调用 | ok=true，耗时 31.7ms（订单查询平均） |
| **同步工具超时** | **503.7ms 返回降级话术**（工具本身要跑 3s）；Agent 回复「系统超时…建议转人工客服」，**未编造订单状态** |
| **连续失败** | 第 1 次真实失败（RuntimeError）→ 第 2、3 次 `circuit_open` 快速失败，不再打 DB |
| 熔断状态 | OPEN，failures=2/阈值2 |
| 半开恢复 | 冷却后进入 HALF_OPEN，探测成功回到 CLOSED |
| 并行执行 | 5 个 300ms 工具并行 < 1s（串行需 1.5s） |
| 并发限流 | 6 工具 / 限流 2，观测峰值 = 2 |

### 工具执行耗时画像（27 次调用）

| 工具 | 调用数 | 平均耗时 | 最大 |
|---|---|---|---|
| queryOrderByOrderNo | 5 | 31.7ms | 38.0ms |
| queryRefundByOrderNo | 3 | 32.0ms | 38.5ms |

这个数据给 P0-1 上下文预算指了方向：**优化重点应是减少不必要的检索调用，
而不是压缩 prompt 文本**。

## 五、评测过程中修正的三个判定缺陷

这三个问题都会导致指标虚高或虚低，值得记录（也是评测系统本身需要迭代的证据）：

### 缺陷 1：`TOOL_ERROR` 误判 6/30（22.2% → 0%）

`ERROR_HINTS` 里用了「异常」作为锚点，而知识库政策正文中出现「异常情况需转人工处理」，
导致检索工具的正常返回被误判为工具报错。

**修正**：改用不可能出现在业务正文里的锚点（`库暂时不可用` / `Traceback` / `Error code:` / 异常类名），
并把「暂时不可用」从 EMPTY_HINTS 移到 ERROR_HINTS（区分「查无此项」与「服务不可用」）。

**影响**：无效调用率从 22.22% 降到 0%，失败归类从 4 类收敛到 2 类。

### 缺陷 2：`REFUSAL_OVER` 误判 3/30

模型正确回答了订单状态、金额、下单时间后，结尾附一句「如需详细物流轨迹，建议转人工客服查询承运信息」——
这是**正常客服兜底话术**，但裁判的 `refused` 标志为 1，被直接判为过度拒答。

**修正**：引入 `_has_substantive_answer()`，要求「裁判判拒答」**且**「回答实质信息量为零」才判过度拒答。
实质信息量的判定用**稳定特征词**（数字、金额、日期、编号），而非整句匹配 ——
因为模型表述与参考要点的措辞天然不同（参考写「订单状态：运输中」，回答写「目前状态为"运输中"」）。

**影响**：`REFUSAL_OVER` 从 3 条降到 0 条。

### 缺陷 3：`MAX_STEP` 被 `LOOP` 覆盖

10 步全是同一工具时，所有步骤都被标为 `LOOP`，「超步数未收敛」这一更根本的失败原因丢失。

**修正**：`MAX_STEP` 优先级高于 `LOOP`。

## 七、已知限制与下一步

### 限制

1. **HALLUCINATION 的判定依赖裁判模型**，存在随机波动（约 3~7 个百分点）。
   与生成评测一致，需跑 3 次取中位数。
2. **HALLUCINATION 的粒度偏粗** —— 裁判只看「参考要点里有没有」，无法区分
   「合理的展开说明」与「真正的编造条款」。当前 4 条里有相当比例可能是误判。
3. **知识库仅 6 个 chunk**，口语化与政策类问题的召回覆盖不足，
   这是 HALLUCINATION 的主要来源，也是当前 Agent 能力的真实天花板。
4. **越界用例仅 4 条**，REFUSAL_UNDER 粒度太粗（错 1 条即 25%）。
5. **未覆盖多轮会话场景** —— 长对话下的上下文累积、记忆污染尚无数据。
6. **可靠性层只在正常路径下跑过** —— 生产环境无故障注入，
   熔断/降级路径靠离线单测与故障注入脚本验证，未纳入常规回归。

### 下一步

| 优先级 | 动作 | 目的 |
|---|---|---|
| 高 | P0-1 上下文预算（`app/context.py`）| 已有 Token 基线（平均 2074/请求），可量化压缩效果；重点是减少不必要的检索调用 |
| 高 | 扩充知识库到 30+ chunk + 扩越界用例到 15 条 | 消除当前评测的主要噪声源，让指标可信 |
| 中 | 引入更细的幻觉判定（条款级比对而非要点级）| 降低 HALLUCINATION 误判率 |
| 中 | P1-2 自定义 StateGraph + checkpoint | 轨迹评测天然覆盖限步、失败恢复、重试降级路径 |
| 中 | 多轮会话场景评测 | 验证记忆与上下文累积的退化曲线 |

## 八、可直接引用的结论

> 构建 Agent 轨迹级评测体系，在 30 条标注用例上量化 pass@1（86.7%）/ 步数分布 /
> 无效调用率（0%）/ 降级调用数（0），并建立 9 类失败归因 taxonomy（检索为空、
> 工具报错、参数非法、重复调用、循环、超步数、幻觉、过度拒答、拒答不足），
> 定位出**知识库召回覆盖不足**是主要瓶颈，83.3% 用例单步收敛。
>
> 配套实现工具执行可靠性层：基于 asyncio 实现超时控制、指数退避重试、
> 熔断降级（CLOSED→OPEN→HALF_OPEN）与并发限流，故障注入实测超时
> 503ms 内返回降级话术且模型未编造数据、连续失败后快速熔断；
> 同时补齐 ReAct 链路 Token 与工具耗时观测（检索 295ms vs 业务工具 30ms）。
